# Recon — Step 0 data exploration

Findings from querying `data/dispatch.db` and loading the five JSON sources directly.
Nothing here is assumed; every claim below was produced by a script rather than read off
`SCHEMA.md`. The queries that produced each non-obvious number are inlined below so any claim
can be re-derived. The recon scripts themselves are deliberately not committed: CLAUDE.md §4
fixes the directory layout and a `scripts/` tree is not in it (see open-questions.md Q-004).

**Reference date used throughout: 2026-08-28** (the day this recon ran).

---

## TL;DR — the five findings that change the build

| # | Finding | Consequence |
|---|---|---|
| 1 | The dataset ends **2026-05-29**, 91 days before today | Any `date('now')` SQL returns **zero rows** for Q1, Q2, Q5, Q8. Half the graded questions silently answer "0". |
| 2 | `product_area` and `modules_active` are **different vocabularies** | The naive module-mismatch check flags 58/85 tickets. The correct mapped check flags 26. |
| 3 | `token_set_ratio` scores a bare substring **100** | `"Fuel"` matches tenants 1 *and* 5 at 100. The resolver must fail closed on multi-tenant hits, not take the top score. |
| 4 | `tank_readings` is **one-to-many** on `customer_id` (900 rows / 30 customers) | The only fan-out trap in the schema. Joining it before aggregating inflates gallons **9.06x**. |
| 5 | `SCHEMA.md` documents enum values that **do not exist** in the data | `shifts.status` and `customers.status` each have exactly one real value. The SQL prompt must carry observed literals, not documented ones. |

## 1. Structure

Six tables, no `sqlite_sequence` fixtures of interest. **No indexes exist on any table** —
not even on `tenant_id`, which every query filters on.

| Table | Rows | tenant_id present |
|---|---:|---|
| `delivery_orders` | 9,769 | yes |
| `shifts` | 5,502 | yes |
| `tank_readings` | 900 | yes |
| `customers` | 114 | yes |
| `drivers` | 114 | yes |
| `trucks` | 72 | yes |

`customers` here means **end-customers** (fuel recipients), *not* tenants. `customers.json`
means tenants. Same word, two entities, one letter of context apart — the SQL prompt must
name this explicitly or the model will answer "how many customers does tenant 3 have?" from
the wrong concept.

`delivery_orders.tenant_id`, `customer_id`, `order_date`, `product_type` and
`gallons_ordered` are `NOT NULL` at the schema level. `driver_id`, `truck_id`,
`delivery_date`, `status` and `priority` are nullable in DDL but 0% null in practice.

## 2. The date gap (finding #1)

```
delivery_orders.order_date      2026-02-27 -> 2026-05-29
delivery_orders.delivery_date   2026-03-02 -> 2026-05-29
shifts.shift_date               2026-03-02 -> 2026-05-29
tank_readings.reading_date      2026-03-03 -> 2026-05-29
tickets.created_at              2026-03-29 -> 2026-05-28
call_transcripts.date           2026-03-16 -> 2026-05-24
```

Today is 2026-08-28. The operational window closed **91 days ago**. Measured impact:

| Question | Anchored on `now()` | Anchored on `MAX(date)` in data |
|---|---:|---:|
| Q1 completed, last 7 days | **0** | 604 |
| Q5 tenant 4 emergency, last 30 days | **0** | 17 |
| Q2 diesel, "last month" | **0** | 558 |

`delivery_orders.created_at` is a single constant (`2026-05-29 10:59:10`) for all 9,769 rows —
it is the generation timestamp of the fixture, not a business event. It must never be used for
date arithmetic. `order_date` and `delivery_date` are the real columns.

**Decision taken:** anchor relative date windows on `MAX(delivery_date)` in the data and state
the anchor in the answer text. See decisions-log.md D-001.

## 3. Observed enum literals (finding #5)

The SQL prompt is built from these, not from `SCHEMA.md`.

```
delivery_orders.status        completed 6851 | in_progress 990 | pending 980 | cancelled 948
delivery_orders.product_type  kerosene 1670 | propane 1659 | diesel 1658
                              gasoline_regular 1611 | heating_oil 1594 | gasoline_premium 1577
delivery_orders.priority      normal 6799 | urgent 1971 | emergency 999
trucks.status                 operational 56 | out_of_service 10 | maintenance 6
drivers.status                active 102 | inactive 12
```

Two documented-but-absent cases:

- `shifts.status` — `SCHEMA.md` documents `'completed' | 'in_progress' | 'cancelled'`.
  All 5,502 rows are `'completed'`. The other two literals never occur.
- `customers.status` — documented as `'active' | 'inactive'`. All 114 rows are `'active'`.

A model told `'inactive'` exists will happily write a filter that correctly returns zero rows,
and the answer will look like a bug. The schema card is generated by **introspection plus
observed distinct values**, not by pasting `SCHEMA.md`.

Answer to Q6 is fixed and date-free: **6 trucks in maintenance**.

## 4. Nulls and the fill-rate question (Q7)

`delivery_orders.gallons_delivered` is null in **2,918 of 9,769 rows (29.87%)**. Every other
column the eight questions touch is 0.00% null.

That 2,918 is not corruption. It is exactly `in_progress (990) + pending (980) + cancelled (948)`.
Completed orders with a null `gallons_delivered`: **0**.

Checked and clean:

```
gallons_delivered > gallons_ordered           0
gallons_ordered IS NULL                       0
gallons_ordered = 0  (division by zero)       0
negative gallons                              0
```

So the anticipated fill-rate corruption is **not present**. Fill rate is safe *provided* the
query filters `status='completed'`; without that filter the numerator silently drops 30% of
rows while the denominator keeps them, producing a plausible-looking ~0.65 instead of ~0.92.
That is the real trap on Q7 — not bad values, but a missing predicate.

Fill rate by tenant (`SUM(delivered)/SUM(ordered)` over completed orders) lands between
**0.9167 (t8) and 0.9268 (t3)** — a tight, believable band that makes a wrong answer hard to
spot by eye. Guard it with a test, not with judgement.

## 5. Fan-out exposure (finding #4)

Baseline: diesel + completed = 1,152 rows, 1,668,862.7 gallons.

| Join added | Rows | Verdict |
|---|---:|---|
| `+ customers` | 1,152 | safe (1:1) |
| `+ drivers` | 1,152 | safe (1:1) |
| `+ trucks` | 1,152 | safe (1:1) |
| `+ customers + tank_readings` | 10,440 | **inflated 9.06x** |

Cardinality check:

```
customers.customer_id       114 rows / 114 distinct   1:1
drivers.driver_id           114 rows / 114 distinct   1:1
trucks.truck_id              72 rows /  72 distinct   1:1
tank_readings.customer_id   900 rows /  30 distinct   ONE-TO-MANY
```

**Only `tank_readings` can inflate an aggregate.** Q2 and Q7 are the exposed questions, and
they are only exposed if the model reaches for `tank_readings`, which neither question needs.
Both should aggregate `delivery_orders` alone and join only to *label* the result.

Referential integrity is otherwise perfect: 0 orphaned foreign keys and **0 cross-tenant
foreign key rows** across all five child→parent relationships. No order references another
tenant's driver, truck or customer. Tenant isolation is not being violated by the data itself —
only, potentially, by the SQL we generate.

## 6. Entity resolution (Step 1 fixture)

All 43 transcripts, 26 distinct `tenant_name` strings, resolved against
`customers.json` + `tenant_aliases.json`:

**Unresolved: 0. Ambiguous: 0.**

```
exact canonical name  ->  11 distinct strings
exact alias           ->  15 distinct strings
normalized / fuzzy    ->   0 needed
```

The alias table is 37 rows, 37 distinct alias strings, and **no alias maps to more than one
tenant**. Every name that actually appears in the transcript data is covered by exact lookup.

This is a genuine finding rather than an absence of one: **fuzzy matching is not needed to
ingest the provided data.** It is needed for free-text tenant names typed by a rep or, more
importantly, mangled by speech-to-text in voice mode. That is where the resolver earns its
cascade, and it is why the fixture below matters more than the transcript list.

### Why the resolver must fail closed

`rapidfuzz.fuzz.token_set_ratio` scores a subset of tokens as a **perfect 100**. Probing the
alias index with partial names:

| Probe | Hits at >=88 | Verdict |
|---|---|---|
| `"Fuel"` | t1, t5 | **ambiguous at score 100** |
| `"Energy"` | t3, t7, t12 | **ambiguous at score 100** |
| `"propane"` | t2, t11 | **ambiguous at score 100** |
| `"Cascade"` | t1 | unique |
| `"Timber"` | t8 | unique |
| `"Summit Energy Group Inc"` | t3 | unique (suffix stripped) |
| `"cascade fuel services llc"` | t1 | unique (suffix stripped) |

A resolver that returns `max(score)` answers `"Fuel"` with tenant 1 at full confidence and
leaks Cascade's data to someone asking about Great Lakes. **The confidence score cannot be the
gate — the count of distinct tenants above the threshold is.** More than one tenant above the
line means `Unresolved` with ranked candidates, regardless of score.

These probes are the seed cases for `tests/test_entity_resolution.py`.

## 7. Cross-source integrity

Tenants 1–12 are present in `customers.json`, `tenant_aliases.json`, `tickets.json` and every
`tenant_id`-bearing DB table except one:

```
db.tank_readings   tenants [1, 3, 6, 9, 10, 12]   missing [2, 4, 5, 7, 8, 11]
```

This is **not** missing data. The six tenants with `tank_readings` rows are *exactly* the six
with `tank_monitor` in `modules_active`. The set equality is perfect. Module entitlement and
operational data agree, which makes `tank_readings` a reliable second signal for the
module-mismatch check.

Every ticket's `tenant_name` resolves to its own `tenant_id`: **0 inconsistencies in 85 tickets.**

## 8. Module mismatch (finding #2)

`product_area` (tickets) and `modules_active` (customers) are different taxonomies that share
three literals:

```
product_area only : billing, integration, login_access, reporting
modules only      : analytics, customer_portal, driver_app, invoicing, route_builder
shared            : dispatch, pricing, tank_monitor
```

A bare `product_area not in modules_active` check flags **58 of 85 tickets** — mostly false
positives, because `integration` and `login_access` are platform-wide and gated by no module
at all. Mapping the two vocabularies first:

```python
AREA_TO_MODULE = {"dispatch": "dispatch", "pricing": "pricing", "tank_monitor": "tank_monitor",
                  "billing": "invoicing", "reporting": "analytics"}
UNGATED = {"integration", "login_access"}
```

gives **26 of 85** genuine mismatches — tickets asking for help with a capability the tenant is
not entitled to. Highest-value cases:

- **t4 Desert Sun** (has only `dispatch`, `pricing`): five `tank_monitor` tickets (#1022, #1023,
  #1025, #1027, #1032, #1083) and it has no `tank_readings` rows either. Both signals agree.
- **t7 Atlantic Coast**: two `tank_monitor` tickets (#1043, #1045) without the module.
- **t8 Timber Ridge**: three `billing` tickets without `invoicing`.

The mapping is a judgement call and is logged as decisions-log.md D-002.

## 9. Tickets, duplicates, and the three mandated triage cases

85 tickets, 2026-03-29 → 2026-05-28. Status `open 33 / closed 20 / pending 16 / resolved 16`.
Priority `medium 34 / urgent 23 / high 15 / low 13`. **37 of 85 have a null `resolution`.**

14 near-duplicate subject pairs within the same tenant (token_set_ratio >= 85). The largest
cluster is four tickets, same tenant, byte-identical subject:

```
t4 'TankLink device not sending data since Tuesday'
   #1025  2026-04-11  pending  urgent
   #1027  2026-04-24  closed   high
   #1083  2026-04-27  open     high
   #1023  2026-05-06  pending  high
```

Note #1027 was **closed** on 04-24 and the issue was refiled twice afterwards. Duplicate
detection has to survive that: "closed" does not mean "resolved".

The three test tickets the assignment mandates are all available:

| Case | Ticket | Why |
|---|---|---|
| (a) low health + expiring contract | **#1083, t4 Desert Sun** | health **28**, contract **expired 2026-07-15**, CARR 36k, 12 open-ish tickets |
| (b) duplicate | **#1083** (of #1023/#1025/#1027) | same tenant, identical subject, 4th filing in 26 days |
| (c) module not active | **#1083** | `tank_monitor` ticket, tenant has only `dispatch` + `pricing` |

Ticket **#1083 is all three at once**, which makes it the single best demo case and also the
one that proves the escalation logic composes signals rather than matching one rule.
Secondary case for (a): **t8 Timber Ridge**, health 39, contract expires 2026-09-10 (13 days).

Also worth noting: **t2 Heartland Propane** has health 45 and a contract expiring
**2026-08-30 — in two days.** It falls outside the assignment's "health < 40" phrasing but is
arguably the most urgent account on the roster. Contract proximity has to be its own signal,
not a tiebreaker under health.

## 12. Scaling notes observed in passing

- **No indexes on any table.** At 12 tenants and 9,769 orders every query is a full scan and it
  does not matter. At 150 tenants and 500K orders each it is the first thing that breaks.
- `delivery_orders.created_at` is a constant — useless for partitioning or incremental loads.
- Dates are stored as TEXT, so all date arithmetic goes through `strftime`/`date()` and cannot
  use an index even once one exists, unless the index is built on the expression.
